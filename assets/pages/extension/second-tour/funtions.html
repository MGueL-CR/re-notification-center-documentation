function enable()

Aquí ya entramos en una zona muy importante, porque enable() es prácticamente el punto donde la extensión cobra vida.

function enable() {

  notificationCenter = new NotificationCenter();
  notificationCenter.startNotificationCenter();
  reloadExtensionOnPrefsChange();
  reloadApplicationProfilesOnPrefsChange();

}

Arrancar el Notification Center

Aquí ocurre algo muy interesante.

notificationCenter.startNotificationCenter();

No basta con crear:new NotificationCenter().

La extensión inmediatamente llama:startNotificationCenter() que ya conocemos de nuestro primer recorrido.

Recordemos que esa función hacía bastantes cosas:

  • agregaba elementos al indicador;
  • modificaba eventsSection;
  • manipulaba messageList;
  • configuraba el scrollView;

Por tanto:

Esto también nos dice que NotificationCenter puede existir antes de estar completamente integrado en GNOME Shell.

function reloadApplicationProfilesOnPrefsChange()

Aquí aparece justamente una de las conexiones que queríamos encontrar. Esta función es pequeña, pero tiene bastante información.

function reloadApplicationProfilesOnPrefsChange() {

  // Reloads Application Profiles when preferences are changed.
  notificationCenter.reloadProfilesSignal =
    notificationCenter.prefs.connect(
      "changed::reload-profiles-signal",
      () => notificationCenter.loadPreferences()
    );

}

¿Qué está haciendo realmente?

Está registrando una señal de GSettings. La pieza clave es:

notificationCenter.prefs.connect(
    "changed::reload-profiles-signal",
    ...
);

En GSettings, una señal con esta forma:changed::NOMBRE_DE_LA_KEY significa:

"Ejecuta esta función cuando cambie específicamente esta key."

Por tanto:

GSettings
   │
   │ cambia "reload-profiles-signal"
   ▼
changed::reload-profiles-signal
   │
   ▼
notificationCenter.loadPreferences()

Y aquí aparece algo que debemos buscar en gschema

Tenemos una key:reload-profiles-signal

Esto significa que el gschema que acabamos de estudiar contiene esa key. Y ahora podemos conectar los dos archivos:

gschema
   │
   └── reload-profiles-signal
             │
             ▼
       extension.js
             │
             └── escucha:
                 changed::reload-profiles-signal

Esto es un ejemplo perfecto de nuestro nuevo mapa de dependencias.

No llama:reloadExtension(); No destruye la extensión. No crea otra instancia.

¿Por qué se llama reload-profiles-signal?

Aquí tenemos una curiosidad. Por el nombre parece una key que no representa realmente una preferencia del usuario, sino que funciona como una especie de señal artificial.

Es decir, probablemente alguien hace algo como:settings.set_int("reload-profiles-signal", ...); o modifica esa key para provocar el evento:changed::reload-profiles-signal y así obligar a la extensión a ejecutar:loadPreferences().

Esto sería un patrón interesante:

No necesariamente:

"el valor significa X"

sino:

"el cambio del valor provoca Y"

function reloadExtensionOnPrefsChange() {

Nuevos puntos confirmados

  • reload-signal es una key de GSettings usada como señal de recarga completa.
  • reload-profiles-signal es una key usada para recargar preferencias/perfiles sin reconstruir todo.
  • Ambas conexiones se almacenan en propiedades del objeto NotificationCenter.
  • Ambas se registran durante enable().
  • Debemos localizar quién modifica ambas keys.
  • Debemos revisar cómo destroy() maneja estas conexiones.
