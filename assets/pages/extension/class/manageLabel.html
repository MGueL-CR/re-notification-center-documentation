manageLabel()

manageLabel:function(nCount,eCount) {
    this.notificationLabel.visible = nCount*this.newNotificationAction;
    this.eventsLabel.visible = eCount*this.newNotificationAction && (this.shouldShowEventsSection() > 0);

    if (this.changeIcons) {
      this.manageIconChange(nCount > 0 || eCount > 0);
    }

    if(this.newNotificationAction == 2) {
      if(nCount>0) {
        this.notificationLabel.text=nCount.toString();
      }
      if(eCount > 0 ) {
        this.eventsLabel.text=eCount.toString();
      }
    }
  }
manageLabel:function(nCount,eCount)

Este método ya no consulta nada, No pregunta: this.notificationSection... Ni: this.prefs...

Porque todo eso ya ocurrió antes. Él simplemente recibe dos datos:

  • nCount → cantidad de notificaciones.
  • eCount → cantidad de eventos.

Eso me gusta porque convierte a manageLabel() en un método bastante independiente.

this.notificationLabel.visible =
    nCount * this.newNotificationAction;

Aquí Selenium-H vuelve a hacer uno de sus "trucos". En lugar de escribir: nCount > 0 && this.newNotificationAction utiliza la multiplicación.

Si imaginamos:

nCount = 3

newNotificationAction = 1

Resultado: 3 JavaScript lo interpreta como verdadero.

Si: nCount = 0 Resultado: 0. Que es falso. Funciona perfectamente, aunque personalmente me cuesta un poco más leerlo.

this.eventsLabel.visible =

Después hace exactamente lo mismo, pero añade una condición extra: this.shouldShowEventsSection() > 0 tiene lógica.

Aunque existan eventos... Si esa sección no debe mostrarse... No tiene sentido enseñar el contador.

if (this.changeIcons) { ... }

¡Ya encontramos el puente con el siguiente método!

Si la preferencia está activada... this.manageIconChange(...) y además le pasa: nCount > 0 || eCount > 0, no le pasa los números, solo le pasa un booleano.

Aquí descubrimos algo que antes solo intuíamos. Parece que newNotificationAction tiene distintos modos. Uno de ellos es: 2 y  cuando vale 2... 

this.notificationLabel.text =
    nCount.toString();

En lugar de mostrar un simple indicador, muestra el número y lo mismo para eventos.

Observa el flujo.

Me gusta una cosa del diseño

  • No hace nada más.
  • No toca el autohide.
  • No toca eventos.
  • No mueve widgets.
  • Solo administra las etiquetas.

Hay un pequeño detalle 

Cuando hace: if(nCount > 0) no escribe: this.notificationLabel.text = "0"; 

Simplemente deja el texto anterior y eso está bien, porque cuando el contador deja de ser visible... El contenido ya no importa.

Mi única observación

Aquí sí habría usado nombres un poco más expresivos.

Por ejemplo: nCount y eCount se entienden.

Pero quizá: notificationCount y eventCount serían todavía más claros.

No es una crítica, solo una mejora de legibilidad que encaja perfectamente en esa futura etapa de refactorización que ya tenemos anotada.
