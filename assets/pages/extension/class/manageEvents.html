manageEvents: function(action) {
    this.eventsSection.visible = this.showEventsSectionIfEmpty || this.shouldShowEventsSection() ;       
    if(this.showEventsInCalendarAlso == true) {
      switch(action) {
        case 0:
          if(this.eventsSectionhere == true) {
            return;
          }
          this.removeSection(this.eventsSection);
          this.box.insert_child_at_index(this.eventsSection,this.showingSections.indexOf("events"));
          this.eventsSectionhere = true;
          return;
        case 1:
          if(this.eventsSectionhere == false) {
            return;
          }
          this.box.remove_child(this.box.get_children()[this.showingSections.indexOf("events")]);
          this.newEventsSectionParent.insert_child_at_index(this.eventsSection, this.eventsSectionPosition);
          this.eventsSectionhere = false;
          return;
      }
    }

A primera vista parece sencillo, pero en realidad es el primer método donde la extensión empieza a mover físicamente componentes de la interfaz. Hasta ahora habíamos visto cargar datos (loadPreferences()), cambiar un estado (dndToggle()) o sincronizar la interfaz (loadDndStatus()). Aquí ya estamos reorganizando el árbol de widgets.

Y hay algo que quiero decir desde el principio. Este método tiene un nombre... que se queda corto. 

Si yo leo manageEvents() pienso: "Va a gestionar los eventos", pero realmente hace algo mucho más específico:

Gestiona la posición y la visibilidad de la sección de eventos.

No gestiona los eventos del calendario en sí, gestiona el widget que los muestra.

this.eventsSection.visible =
    this.showEventsSectionIfEmpty ||
    this.shouldShowEventsSection();

Traducida al español sería:

"La sección de eventos será visible si:

  • el usuario quiere verla aunque esté vacía, o
  • realmente existen eventos que mostrar."

Es una condición muy natural.

if(this.showEventsInCalendarAlso == true)

Aquí recordé inmediatamente algo que vimos en loadPreferences(). ¿Recuerdas?

this.showEventsInCalendarAlso =
(
    this.eventsSectionToBeShown &&
    this.eventsSectionPosition != 1

Así que ya sabemos exactamente qué significa, si esta variable es falsa... Todo el resto del método ni siquiera se ejecuta.

switch(action)

Ahora viene el famoso action y aquí quiero detenerme.

Primera observación

Este método recibe un parámetro manageEvents(action), pero... No sabemos todavía quién lo llama con 0 y quién con 1.

Y eso está bien, no hace falta inventarlo, solo podemos deducir lo que significan.

Case 0:

Primero pregunta: Si ya está donde debe estar... No hace nada, eso evita trabajo innecesario.

if(this.eventsSectionhere == true)

Aquí ocurre algo importante. No la destruye, no la elimina, solo la desacopla de donde estaba.

this.removeSection(this.eventsSection);

¡Ahora sí! La vuelve a insertar, pero en otro sitio.

this.box.insert_child_at_index(
    this.eventsSection,
    ...
);

Marca internamente:

"La sección ya está aquí."
this.eventsSectionhere = true;
Case 1:

Es exactamente el proceso inverso.

if(this.eventsSectionhere == false)

Primero pregunta: Si ya no está aquí... No hace nada.

Después, la saca.

this.box.remove_child(...)

Para luego insertarla en otro contenedor.

this.newEventsSectionParent.insert_child_at_index(...)

Y finalmente actualiza el estado.

this.eventsSectionhere = false;

En resumen

Lo que realmente hace el método no crea una segunda sección. Es exactamente el mismo widget moviéndose de un contenedor a otro. Y eso me parece una decisión muy inteligente.

Sobre action

Aquí sí quiero hacer una pequeña apuesta para el futuro, no sobre el código, sino sobre el diseño. 

Creo que: action = 0 significa:

"Mover la sección al panel principal."

Y action = 1 significa:

"Mover la sección junto al calendario."

No puedo afirmarlo todavía, pero me parece la interpretación más coherente con lo que vemos.

Una pequeña crítica constructiva

Este es el primer método donde quizá habría usado un enum o constantes.

Porque leer: manageEvents(0) no dice absolutamente nada. Mientras que algo como: manageEvents(MOVE_TO_MAIN_BOX); o manageEvents(MOVE_TO_CALENDAR); haría el código mucho más expresivo.

Claro, estamos hablando de un proyecto escrito hace varios años y en el estilo de GJS de aquella época. No es un error, simplemente una decisión de diseño que hoy probablemente escribiríamos de otra manera.
