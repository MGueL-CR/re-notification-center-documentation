Ahora entramos en una fase distinta de startNotificationCenter(). Hasta ahora el método se dedicó principalmente a construir la extensión. A partir de aquí empieza a decirle a GNOME:

"Cuando ocurra esto... avísame."

Es decir, pasamos de construcción a eventos.

Lo primero que veo... Otra vez aparece un comentario.

//this.indicatorViewShortcut();

No es malo ni bueno; simplemente es una pista sobre cómo fue evolucionando el proyecto.

Main.wm.addKeybinding(...)

Aquí aparece un objeto nuevo.

Main.panel

Ahora conocemos: 
Main.wm

¿Qué crees que significa ese wm?

No hace falta saberlo con certeza, pero por el contexto yo apostaría por:

Window Manager

Y tiene sentido. ¿Quién registra los atajos del teclado? El gestor de ventanas.

El nombre addKeybinding es casi perfecto.

Registrar un atajo de teclado. 
add    +    Key    +    Binding
  • Primer parámetro
    • 'indicator-shortcut'
    No dice: 
    "Ctrl+Alt+N"
    Dice: 
    "indicator-shortcut"
    ¿Por qué?

    Porque el atajo probablemente está definido en el gschema. La extensión solo dice:

    "Usa el atajo configurado para indicator-shortcut."
    Eso significa que el usuario puede cambiarlo sin modificar el código.
  • Segundo parámetro
    • this.prefs

    El gestor de ventanas necesita saber dónde buscar la configuración y por eso recibe el objeto GSettings.

  • Tercer parámetro
    • MetaKeyBindingFlags.NONE

    Aquí todavía no sabemos qué opciones existen. Lo único que sabemos y con eso basta por ahora es:

    "No está usando ninguna bandera especial."
  • Cuarto parámetro
    • ShellActionMode.NORMAL |
ShellActionMode.OVERVIEW |
ShellActionMode.POPUP

    Aquí sí podemos deducir bastante. Está diciendo:

    "Este atajo funciona cuando GNOME está en estos modos."

    Visualmente sería algo así:

    ✓ Escritorio normal

✓ Vista de Actividades (Overview)

✓ Cuando hay un Popup abierto

    Es decir, no limita el atajo únicamente al escritorio. Eso me parece una decisión muy buena desde el punto de vista de la experiencia de usuario.


    Llegamos al callback 
    () => {

    Todo lo que hay aquí ocurre cuando el usuario presiona el atajo. 

    this.notificationIcon.visible =
    !(this.mediaIcon.visible || this.eventsIcon.visible);

    Aquí Selenium-H nos lanza una expresión lógica interesante. Vamos paso a paso.

  • ¿Está visible el icono multimedia?
    • this.mediaIcon.visible
  • ¿Está visible el icono de eventos?
    • this.eventsIcon.visible
  • ¿Hay alguno visible?
    • A || B
  • Para finalmente:
    • !(...)

    Invertimos el resultado. En otras palabras:

    Si ya hay un icono visible

↓

No muestres el icono de notificaciones.

    Porque probablemente solo quiere mostrar un indicador a la vez. 

    this.visible = true;

    Eso también me gusta. Imagina que el usuario ocultó el botón automáticamente.

    Al pulsar el atajo... Lo vuelve visible y tiene sentido.
    this.menu.toggle();

    Y aquí ya no hay misterio. Abre el menú:

    Si estaba abierto... Lo cierra.
    Si estaba cerrado... Lo abre.

    ¿Qué acabamos de aprender?

    Este bloque no crea ningún widget, no modifica la interfaz, no mueve componentes. Simplemente registra un evento del sistema.

    Es decir:

    Usuario pulsa el atajo
↓

GNOME llama al callback
↓

La extensión decide qué hacer

    Eso ya mejora bastante. Incluso iría un paso más allá... El callback también puede tener nombre.

    En lugar de:

    () => {

    this.notificationIcon.visible = ...

    this.visible = true;

    this.menu.toggle();

}

    Podría ser:

    () => this.toggleNotificationCenter()

    Y crearíamos:

    toggleNotificationCenter: function() {

    this.notificationIcon.visible =
        !(this.mediaIcon.visible || this.eventsIcon.visible);

    this.visible = true;

    this.menu.toggle();

}
