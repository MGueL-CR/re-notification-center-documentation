Los números mágicos

Recordemos esta condición:

(!this.isDndOff) * this.autohide > 1

Cuando la vimos dijimos:

"Está un poco extraña..."

Ahora ya sabemos por qué.

Si sustituimos los valores del enum: 
false = 0
true  = 1
dnd   = 2
Queda así:
autohide Resultado
0 Nunca entra.
1 Tampoco cumple > 1.
2 Sí cumple cuando DND está activo.

Es decir, Selenium-H aprovechó el valor numérico del enum para distinguir el tercer comportamiento sin escribir otro switch.

¿Me gusta esa implementación?

Funciona, pero aquí sí haría una observación para nuestras notas.

Desde el punto de vista de la legibilidad, hoy probablemente escribiríamos algo como:

switch (this.autohide) {
    case AUTOHIDE.FALSE:
        ...
        break;

    case AUTOHIDE.TRUE:
        ...
        break;

    case AUTOHIDE.DND:
        ...
        break;
}

Porque expresa la intención mucho mejor.

La implementación actual depende de recordar que: 2 = dnd y eso solo lo sabemos porque acabamos de leer el gschema.xml.

Algo interesante

Este es el primer caso donde el schema explica una decisión que en extension.js parecía un poco "mágica".

Sin conocer el enum, la condición: this.autohide > 1 era un número sacado de la nada.

Ahora sabemos que no es un número arbitrario, sino el tercer valor de una enumeración y eso elimina bastante misterio.

Y aquí me pasó algo curioso: cuando estudiamos manageAutohide() pensé "esa comparación con > 1 es un poco rara". Resultó que Selenium-H no estaba haciendo un truco extraño; simplemente estaba aprovechando la codificación numérica del enum. Sin el gschema.xml eso parecía una "constante mágica". Con el schema, la pieza encaja perfectamente. Esa es justamente la ventaja de recorrer ahora la configuración: estamos iluminando zonas de extension.js que antes parecían un poco oscuras.

Un patrón muy claro

Y ya empezamos a notar un patrón muy claro de Selenium-H: le gustaba que sus enumeraciones fueran "inteligentes". No las usaba solo para nombrar estados; también escogía cuidadosamente los valores (0, 1, 2) para simplificar ciertas condiciones matemáticas dentro del código. Es un estilo muy característico y, ahora que lo identificamos, seguramente volveremos a verlo en los siguientes enum.

Durante el recorrido por extension.js, varias veces vimos cosas como: 

this.eventsSectionPosition != 1
this.autohide > 1
if (this.newNotificationAction == 2)

En ese momento parecían "números mágicos". Ahora el gschema.xml nos está diciendo que no eran mágicos, sino referencias directas a los valores de los enum.

Por ejemplo:

Código en extension.js Traducción después de leer el schema
== 0 "El usuario eligió la primera opción."
== 1 "El usuario eligió la segunda opción."
== 2 "El usuario eligió la tercera opción."

De hecho... Empiezo a pensar que Selenium-H tenía una filosofía bastante clara.

En lugar de escribir:

switch (this.newNotificationAction) {
    case NONE:
    case EMPTY:
    case COUNT:
}

Prefería diseñar el enum para luego hacer: if (this.newNotificationAction == 2) o this.newNotificationAction * valor

Es decir, primero pensaba el valor del enum y luego escribía el código alrededor de él.

Eso tiene una consecuencia interesante, el gschema.xml deja de ser un simple archivo de configuración. Se convierte casi en parte del algoritmo.

Porque si alguien cambiara:

none  = 0
empty = 1
count = 2

Por:

none  = 10
empty = 20
count = 30

La extensión seguiría compilando... pero dejaría de funcionar correctamente.

Una nota para RE: Notification Center

Aquí sí anotaría una observación para el futuro, no como un cambio urgente, sino como un principio de diseño:

Evitar que la lógica dependa de los valores numéricos de un enum cuando esos valores representan conceptos, no cantidades.

Es decir, preferir: switch (this.newNotificationAction) sobre: if (this.newNotificationAction == 2)

No porque la implementación actual sea incorrecta, sino porque desacopla el algoritmo de la codificación interna del enum.

Nueva observación

Patrón identificado: Selenium-H aprovecha los valores enteros de los enum como parte de la lógica del programa, no solo como identificadores de opciones.

Eso es exactamente el tipo de patrón que queríamos descubrir al leer el código. No aparece documentado en ningún sitio, pero ahora que lo vimos dos veces (autohide y new-notification), ya sabemos que no es una casualidad, sino una decisión de diseño del autor.

Primera mejora de refactorización

Y aquí creo que acabamos de encontrar la primera mejora de refactorización con una justificación técnica sólida, no una cuestión de gustos y esa diferencia es muy importante.

Hoy el código dice...

if (this.newNotificationAction == 2) {
    ...
}

La pregunta que se hace cualquier persona que lo lea es:

¿Qué representa el 2?

Y la respuesta es... "Depende de que hayas leído antes el gschema.xml." Eso crea una dependencia innecesaria.

En cambio, imagina algo así en loadPreferences():

const NewNotificationAction = {
    NONE: 0,
    EMPTY: 1,
    COUNT: 2
};

Y luego:

if (this.newNotificationAction == NewNotificationAction.COUNT) {
    ...
}

Ahora la lectura cambia completamente.

Ya no preguntas: ¿Qué es el 2?

Ahora lees directamente: "Ah, esta condición solo aplica cuando la acción es COUNT."

O incluso mejor, como es una extensión pequeña, podría declararse una sección de constantes al inicio del archivo. 

const EventsPosition = {
    BELOW: 0,
    DONTSHOW: 1,
    BESIDE: 2
};

const DndPosition = {
    NONE: 0,
    TOP: 1,
    BOTTOM: 2
};

const AutohideMode = {
    NEVER: 0,
    AUTO: 1,
    DND: 2
};

const NotificationMode = {
    NONE: 0,
    EMPTY: 1,
    COUNT: 2
};

Y a partir de ahí todo el código se vuelve muchísimo más expresivo.

La gran ventaja

Fíjate en este ejemplo.

Hoy vemos:

if (this.autohide > 1)

Nosotros ya sabemos que significa:

"Modo DND."

Pero dentro de un año... Ni tú ni yo nos vamos a acordar.

En cambio:

if (this.autohide == AutohideMode.DND)

No necesita comentarios.

No necesita abrir el XML.

No necesita memoria.

Y lo mejor esto:

  • No cambia absolutamente nada del comportamiento.
  • No rompe compatibilidad.
  • No modifica el gschema.xml.
  • No cambia GSettings.
  • No cambia las preferencias.

Solo mejora la legibilidad y esas son mis mejoras favoritas.

REF-001 — Eliminar números mágicos asociados a enum

Problema

En varios lugares de extension.js se comparan directamente valores enteros provenientes de GSettings. Ejemplos:

== 0
== 1
== 2
> 1

Su significado solo puede entenderse consultando gschema.xml.

Propuesta

Crear constantes descriptivas para cada enumeración y sustituir las comparaciones numéricas por nombres.

Ejemplo: NotificationMode.COUNT en lugar de 2

Beneficios

  • Código más legible.
  • Menor dependencia del gschema.xml para entender la lógica.
  • Evita errores si algún día cambian los valores del enum.
  • Facilita el mantenimiento futuro.

Esta propuesta nació de entender el código, no de querer modernizarlo porque sí. Si hubiéramos abierto el proyecto el primer día, probablemente habríamos dicho:

"Vamos a cambiar todos los números por constantes."

Hoy la razón es mucho mejor. Sabemos exactamente:

  • por qué existen esos números;
  • de dónde vienen;
  • cuándo conviene sustituirlos;
  • y qué beneficio concreto aporta hacerlo.
