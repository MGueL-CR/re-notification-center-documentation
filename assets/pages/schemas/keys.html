Las Keys

Ahora sí entramos en la parte que, personalmente, creo que será la más enriquecedora del gschema.xml.

Hasta ahora vimos: Enums, es decir:

¿Qué tipos de valores existen?

Ahora vamos a ver: Keys, es decir:

¿Qué preferencias reales almacena la extensión?

Y precisamente aquí es donde empezarán a unirse todas las piezas.

Lo que espero encontrar en cada <key>

A partir de ahora, propongo que analicemos cada key siempre con la misma plantilla, igual que hicimos con los métodos de extension.js.

Nombre: ¿Qué representa esa preferencia?
name="..."
Tipo: ¿Es?
  • boolean
  • int
  • string
  • enum
  • otro
Valor por defecto: ¿Qué ocurre si el usuario nunca modifica esa preferencia?
Descripción: La tomamos como la intención original del autor.

Si el archivo incluye: <summary> o <description>

Relación con el código

Aquí sí recordaremos cosas como:

"Este key alimenta this.notificationCount."

O

"Este lo vimos en startNotificationCenter()."
Posibles mejoras:

No para implementarlas todavía, solo para anotarlas.

Por ejemplo:

  • nombres más claros,
  • eliminar números mágicos,
  • simplificar lógica.

Creo que ahora el estudio se volverá mucho más interesante, porque cada key será un puente entre:

gschema.xml
        ↓
prefs.js
        ↓
extension.js

Y, poco a poco, iremos entendiendo cómo fluye una preferencia desde que el usuario la cambia hasta que modifica el comportamiento de la extensión.

Key: "show-media"

Este primer key es una buena introducción porque es bastante sencillo.

<key name="show-media" type="i">
  <default>1</default>
  <summary>Show Media Section on Notification Center</summary>
  <description>Show Media Section on Notification Center</description>
</key>

1. Nombre:

El nombre es bastante descriptivo.

name="show-media"

Representa una preferencia relacionada con:

Mostrar la sección multimedia dentro del Centro de Notificaciones.

2. Tipo

Aquí aparece algo curioso.

type="i"

Es un entero (i), no un booleano.

¿Por qué un entero?

Si únicamente leyéramos el nombre: show-media Uno esperaría: type="b" con:

<default>true</default>

Pero no, eligió un entero. Eso nos hace sospechar que:

  • no es simplemente Mostrar / Ocultar;
  • probablemente utiliza alguno de los enums que vimos anteriormente.

Todavía no podemos afirmarlo hasta encontrar el código que lo lee.

3. Valor por defecto

El valor inicial será: 1

<default>1</default>

Y como todavía no sabemos su interpretación exacta, solo podemos afirmar eso.

Más adelante veremos si corresponde a algún enum o a:

  • mostrar,
  • ocultar,
  • automático,

4. Summary

Aquí el propósito es claro.

Show Media Section on Notification Center

Es el texto que explica qué controla esta preferencia.

5. Description

Aquí Selenium-H fue bastante práctico, repitió exactamente el mismo texto.

Show Media Section on Notification Center

No añadió una explicación más extensa. Es totalmente válido, aunque muchos proyectos aprovechan el <description> para dar más contexto.

6. Relación con extension.js

Y esto nos recuerda inmediatamente a algo que vimos en extension.js: this.mediaSection.visible = this.mediaSection._shouldShow(); y también existía: this.mediaCount++;

Es decir, ya sabemos que la extensión tiene una sección dedicada a los controles multimedia.

7. Una pequeña observación

Aquí ya vemos una diferencia interesante entre el nombre y el tipo.

El nombre sugiere: Mostrar multimedia pero el tipo dice: Entero

Eso nos recuerda una regla que creo que será útil durante todo el estudio:

Nunca asumir el comportamiento por el nombre.

Siempre mirar:

  • el tipo,
  • el valor por defecto,
  • y dónde se utiliza en el código.

Por defecto la extensión no modifica la posición del calendario.

<default>false</default>

Es decir, respeta el diseño original de GNOME hasta que el usuario decida cambiarlo.

Show Calendar on Left

5. Description

Igual que el Summary.

6. Relación con el proyecto

Aquí ya conocemos el comportamiento porque lo vimos durante el análisis de extension.js.

Recordemos que la extensión reorganizaba partes del menú de fecha (dateMenu) y movía algunas secciones.

Este key gobierna precisamente una de esas modificaciones de la interfaz: decidir si el calendario permanece en su posición original o si se coloca al lado izquierdo.

Por lo tanto, este key participa en la construcción visual del panel del Centro de Notificaciones.

7. Observación de diseño

Este key me parece un buen ejemplo de cuándo no utilizar un enum.

Podría haberse hecho algo así:

LEFT
RIGHT

Pero habría sido innecesario, solo hay dos estados posibles, así que un booleano es mucho más limpio.

Otra pequeña observación, empiezo a notar una organización bastante lógica en los key.

Hasta ahora hemos visto:

  • Visibilidad de secciones (show-*)
  • Posición de secciones (events-position)
  • Comportamiento automático (autohide-*)
  • Distribución de la interfaz (calendar-on-left)

No están agrupados al azar; parece que Selenium-H fue ordenando las preferencias por áreas funcionales de la extensión, lo que hace que el gschema.xml sea mucho más fácil de recorrer. Esa organización ya empieza a reflejar la estructura que conocimos previamente en extension.js.

Key: "sections-order"

Este key es muy interesante porque introduce un tipo de dato que todavía no habíamos visto.

<key name="sections-order" type="as">
  <default>['media','notification','events']</default>
  <summary>Order of sections in Notification Center</summary>
  <description>Order of sections in Notification Center</description>
</key>

1. Nombre

name="sections-order"

Describe exactamente su función:

Define el orden en que se mostrarán las secciones del Centro de Notificaciones.

Ya no controla si una sección existe o no. Controla la secuencia en que aparecerán.

2. Tipo

Aquí aparece un tipo nuevo.

type="as"

as significa: Array of String, es decir:

a  = Array
s  = String

3. Valor por defecto

Aquí ya no tenemos un único valor.

<default>['media','notification','events']</default>

Tenemos una lista ordenada:

1. media
2. notification
3. events

Y aquí está la clave: El orden tiene significado.

Si el usuario cambia la preferencia a:

[
    "events",
    "media",
    "notification"
]

La extensión reorganizará la interfaz en ese mismo orden.

4. Summary

Muy claro.

Order of sections in Notification Center

5. Description

Igual que el Summary.

6. Relación con el proyecto

Este key lo vimos reflejado durante el análisis de extension.js.

Recordemos que existía lógica que construía las tres secciones:

  • mediaSection
  • notificationSection
  • eventsSection

Y posteriormente las insertaba dentro del contenedor.

Este key es precisamente el que decide en qué orden deben agregarse, es decir, no cambia el contenido de las secciones, cambia la forma en que se distribuyen visualmente.

7. Una observación

Este key demuestra una buena decisión de diseño. Selenium-H no creó tres booleanos como:

media-first
notification-first
events-first

Ni tampoco creó un enum gigantesco con todas las combinaciones posibles.

Eso habría sido una pesadilla. En cambio dijo:

"Voy a guardar simplemente una lista ordenada."

Eso hace que el sistema sea mucho más flexible. Con tres elementos existen: 3! = 6 combinaciones posibles. Con un array no hace falta crear seis enums distintos.

Aquí también vemos otra fortaleza de GSettings, no solo almacena tipos simples. También puede almacenar colecciones, eso amplía bastante las posibilidades del esquema.

Este key es otro ejemplo donde el diseño del esquema refleja muy bien el problema que intenta resolver.

<key enum="org.gnome.shell.extensions.notification-center.clear-button-alignment"
     name="clear-button-alignment">
  <default>'right'</default>
  <summary>Clear All Button position</summary>
  <description>Clear All Button position</description>
</key>

1. Nombre

Controla la alineación del botón "Clear All" (Borrar todo).

clear-button-alignment

Y aquí inmediatamente recordé que durante extension.js vimos la creación del botón: this.clearButton y también cómo se agregaba al contenedor correspondiente.

Este key no controla el botón en sí, sino dónde se coloca dentro de su contenedor.

2. Tipo

Este enum ya lo estudiamos.

enum="org.gnome.shell.extensions.notification-center.clear-button-alignment"

Sus valores eran:

left
center
right
hide

Aquí encontramos algo interesante. Este enum no solo representa una posición.

También incorpora un comportamiento: hide , es decir, reutiliza el mismo mecanismo (enum) para representar tanto la ubicación como la posibilidad de no mostrar el botón.

Me parece una decisión acertada porque evita crear un booleano adicional como: show-clear-button

3. Valor por defecto

<default>'right'</default>

Por defecto:

Clear All
        ↓
     derecha

Y creo que coincide con lo esperado visualmente.

4. Summary

Describe correctamente la finalidad.

Clear All Button position
5. Description

Igual que el Summary.

6. Relación con el proyecto

Ya conocemos el recorrido.

Durante extension.js vimos:

  • la creación del botón,
  • su inserción en el contenedor,
  • y el uso de la preferencia correspondiente para decidir dónde colocarlo.

Por tanto, este key gobierna la alineación visual del botón "Clear All".

7. Una observación interesante

Este enum es uno de mis favoritos hasta ahora.

¿Por qué? Porque combina dos conceptos relacionados:

left
center
right

y además: hide, en lugar de hacer esto:

alignment
showButton

Lo resolvió con un único enum.

Desde el punto de vista del usuario tiene bastante sentido:

"¿Dónde quieres el botón?"
  • Izquierda.
  • Centro.
  • Derecha.
  • No lo quiero.

Todo forma parte de la misma decisión.
