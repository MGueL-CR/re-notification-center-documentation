Las Keys

Ahora sí entramos en la parte que, personalmente, creo que será la más enriquecedora del gschema.xml.

Hasta ahora vimos: Enums, es decir:

¿Qué tipos de valores existen?

Ahora vamos a ver: Keys, es decir:

¿Qué preferencias reales almacena la extensión?

Y precisamente aquí es donde empezarán a unirse todas las piezas.

Lo que espero encontrar en cada <key>

A partir de ahora, propongo que analicemos cada key siempre con la misma plantilla, igual que hicimos con los métodos de extension.js.

Nombre: ¿Qué representa esa preferencia?
name="..."
Tipo: ¿Es?
  • boolean
  • int
  • string
  • enum
  • otro
Valor por defecto: ¿Qué ocurre si el usuario nunca modifica esa preferencia?
Descripción: La tomamos como la intención original del autor.

Si el archivo incluye: <summary> o <description>

Relación con el código

Aquí sí recordaremos cosas como:

"Este key alimenta this.notificationCount."

O

"Este lo vimos en startNotificationCenter()."
Posibles mejoras:

No para implementarlas todavía, solo para anotarlas.

Por ejemplo:

  • nombres más claros,
  • eliminar números mágicos,
  • simplificar lógica.

Creo que ahora el estudio se volverá mucho más interesante, porque cada key será un puente entre:

gschema.xml
        ↓
prefs.js
        ↓
extension.js

Y, poco a poco, iremos entendiendo cómo fluye una preferencia desde que el usuario la cambia hasta que modifica el comportamiento de la extensión.

Key: "show-media"

Este primer key es una buena introducción porque es bastante sencillo.

<key name="show-media" type="i">
  <default>1</default>
  <summary>Show Media Section on Notification Center</summary>
  <description>Show Media Section on Notification Center</description>
</key>

1. Nombre:

El nombre es bastante descriptivo.

name="show-media"

Representa una preferencia relacionada con:

Mostrar la sección multimedia dentro del Centro de Notificaciones.

2. Tipo

Aquí aparece algo curioso.

type="i"

Es un entero (i), no un booleano.

¿Por qué un entero?

Si únicamente leyéramos el nombre: show-media Uno esperaría: type="b" con:

<default>true</default>

Pero no, eligió un entero. Eso nos hace sospechar que:

  • no es simplemente Mostrar / Ocultar;
  • probablemente utiliza alguno de los enums que vimos anteriormente.

Todavía no podemos afirmarlo hasta encontrar el código que lo lee.

3. Valor por defecto

El valor inicial será: 1

<default>1</default>

Y como todavía no sabemos su interpretación exacta, solo podemos afirmar eso.

Más adelante veremos si corresponde a algún enum o a:

  • mostrar,
  • ocultar,
  • automático,

4. Summary

Aquí el propósito es claro.

Show Media Section on Notification Center

Es el texto que explica qué controla esta preferencia.

5. Description

Aquí Selenium-H fue bastante práctico, repitió exactamente el mismo texto.

Show Media Section on Notification Center

No añadió una explicación más extensa. Es totalmente válido, aunque muchos proyectos aprovechan el <description> para dar más contexto.

6. Relación con extension.js

Y esto nos recuerda inmediatamente a algo que vimos en extension.js: this.mediaSection.visible = this.mediaSection._shouldShow(); y también existía: this.mediaCount++;

Es decir, ya sabemos que la extensión tiene una sección dedicada a los controles multimedia.

7. Una pequeña observación

Aquí ya vemos una diferencia interesante entre el nombre y el tipo.

El nombre sugiere: Mostrar multimedia pero el tipo dice: Entero

Eso nos recuerda una regla que creo que será útil durante todo el estudio:

Nunca asumir el comportamiento por el nombre.

Siempre mirar:

  • el tipo,
  • el valor por defecto,
  • y dónde se utiliza en el código.

Key: "show-notification"

<key name="show-notification" type="i">
  <default>2</default>
  <summary>Show Notifications list on Notification Center</summary>
  <description>Show Notifications list on Notification Center</description>
</key>

1. Nombre

Controla la lista de notificaciones que aparece dentro del Centro de Notificaciones.

name="show-notification"

No habla del banner emergente. No habla del contador. Habla específicamente de la lista.

2. Tipo

Nuevamente tenemos un entero: type="i" y esto ya deja de parecer casualidad.

Ahora tenemos:

show-media         → entero
show-notification  → entero

Esto empieza a indicar que Selenium-H tenía un patrón de diseño.

3. Valor por defecto

Aquí aparece algo interesante. El anterior tenía: 1. Este tiene: 2.

<default>2</default>

Eso prácticamente confirma que no estamos ante un simple Mostrar/Ocultar.

Porque si fuera un booleano disfrazado de entero esperaríamos:

0 = ocultar
1 = mostrar

Pero aquí el valor inicial ya es 2. Eso nos dice que seguramente existen varios estados posibles.

4. Summary

Muy claro.

Show Notifications list on Notification Center

Controla la visualización de la lista de notificaciones.

5. Description

Igual que el Summary. No añade información adicional.

6. Relación con extension.js

Aquí ya conocemos varios candidatos.

Durante el análisis vimos: this.notificationSection. También: this.notificationSection.visible

Y en _onOpenStateChanged(): 

this.notificationSection.visible =
    this.notificationSection._list.get_children().length;

Así que seguramente este key termina afectando esa parte del código.

7. Una pequeña observación

Empiezo a ver un patrón, los dos primeros key son:

show-media
show-notification

Y ambos:

  • usan type="i";
  • tienen un valor por defecto distinto de 0.

Eso me hace pensar que probablemente ambos compartan el mismo enum.

Todavía no podemos afirmarlo porque aún no hemos llegado a la definición del key con enum="..." (si existe), pero ya es una hipótesis bastante fuerte.

Y te comparto algo que me está dejando este bloque.

Cuando empezamos los key, pensé que cada uno sería independiente. Ahora empiezo a sospechar que los primeros key están organizados por familias.

Por ejemplo:

Familia "mostrar secciones"
    
    show-media
    show-notification
    ...

Si el siguiente key también resulta ser un entero relacionado con otra sección de la interfaz, esa hipótesis empezará a tomar bastante fuerza.

Key: "events-position"

Este key es el primero que rompe el patrón de los anteriores y precisamente por eso es muy interesante.

<key enum="org.gnome.shell.extensions.notification-center.events-position"
     name="events-position">
  <default>'below'</default>
  <summary>Also, Show Events List</summary>
  <description>Also, show Events List</description>
</key>

1. Nombre

Ya lo conocemos.

name="events-position"

Durante extension.js vimos: his.eventsSectionPosition = this.prefs.get_enum("events-position");

Y además analizamos el enum correspondiente:

<enum id="org.gnome.shell.extensions.notification-center.events-position">
    <value nick="below" value="0"/>
    <value nick="hide" value="1"/>
    <value nick="beside" value="2"/>
</enum>

Así que este key utiliza ese enum.

2. Tipo

Aquí aparece una novedad, observa que ya no tiene: type="i" Ahora tiene:

enum="org.gnome.shell.extensions.notification-center.events-position"

Es decir, este key es de tipo enum

3. Valor por defecto

Aquí viene otra diferencia muy elegante.

<default>'below'</default>

No aparece: default>0</default>, aparece el nick.

Eso significa que el autor escribe: below y GSettings sabe convertirlo internamente en: 0

Me gusta muchísimo esto, porque el archivo queda mucho más legible.

Compara: default>0</default> vs default>'below'</default>

No hay discusión, la segunda opción explica sola la intención.

4. Summary

Aquí sí tengo una observación, el texto me parece un poco ambiguo.

Also, Show Events List

Yo hubiera esperado algo como: Events section position o Position of the events section

Porque el nombre del key habla de posición. El summary habla de mostrar, no son exactamente la misma idea.

5. Description

Igual que el Summary.

6. Relación con extension.js

Aquí ya no necesitamos hacer hipótesis.

Ya vimos esto:

this.eventsSectionPosition =
    this.prefs.get_enum("events-position");

Y posteriormente aparecían decisiones como: witch(this.eventsSectionPosition) o comparaciones similares. Así que el recorrido ya lo conocemos.

7. Una observación

Este key confirma una sospecha que tuvimos hace un rato.

Los primeros key eran: 

show-media
show-notification
show-events

Y usaban: type="i" Ahora este utiliza: enum="..."

Eso me hace pensar que los tres anteriores no están usando un enum, sino que realmente almacenan un entero cuyos valores interpreta el código. Es decir, ya no estoy tan convencido de mi hipótesis anterior de que compartían un enum.
