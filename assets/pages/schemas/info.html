¿Qué es Schema?

¿En gschema se almacenan las configuraciones?

El gschema.xml no almacena la configuración del usuario. Define cómo es la configuración, es decir, es como un "contrato" o una "plantilla".

Una analogía con una clase Java, imagina esto:

class Settings {
    boolean showLabel = true;
    int bannerPosition = 2;
}

Esta clase define:

  • qué variables existen;
  • de qué tipo son;
  • cuál es su valor inicial.

Pero cuando creas un objeto: Settings s = new Settings(); los cambios que hagas: s.showLabel = false; no modifican la clase.

Solo modifican la instancia. El gschema.xml es muy parecido a esa clase.

Entonces, ¿dónde se guardan los cambios?

Aquí entra GSettings.

Cuando el usuario cambia una preferencia desde prefs.js, GNOME ya no vuelve a escribir el gschema.xml.

Lo que hace es guardar únicamente los valores modificados en una base de datos de configuración llamada dconf. Es decir:

gschema.xml
        │
        │ define
        ▼
GSettings
        │
        │ guarda cambios
        ▼
dconf
Ejemplo:

En el gschema.xml tienes: <default>2</default>, pero el usuario nunca toca esa opción.

Entonces GSettings simplemente usa: 2 y no hace falta guardar nada.

Pero si el usuario cambia el valor a: 0 Entonces dconf guarda únicamente: show-notification = 0

El resto de preferencias siguen usando los valores por defecto del gschema.xml.

Eso tiene una ventaja enorme, imagina que existen 80 preferencias. Si solo cambias dos... dconf solo almacena esas dos.

Las otras 78 se leen directamente del valor por defecto definido en el esquema. Es un sistema muy eficiente.

Conceptos a considerar:

  • gschema.xml → Define la estructura de las preferencias (tipos, nombres y valores por defecto). Es de solo lectura durante la ejecución.
  • GSettings → API que lee el esquema y proporciona acceso a las preferencias.
  • dconf → Almacena los cambios realizados por el usuario. Si una preferencia nunca se modifica, simplemente se utiliza el valor por defecto del gschema.xml.

Y si en algún momentos nos preguntamos o nos decimos:

"Veamos dónde está almacenado ese dconf."

Ahí seguramente terminaremos usando comandos como:

gsettings list-recursively org.gnome.shell.extensions.notification-center
dconf dump /org/gnome/shell/extensions/notification-center/

Para ver exactamente qué está guardado.

Y hay un detalle que me gusta mucho de este diseño: el esquema nunca se modifica. Eso significa que puedes actualizar la extensión, reinstalarla o incluso compartir el mismo gschema.xml con miles de usuarios, mientras que cada uno conserva su propia configuración personal en dconf. Es una separación muy limpia entre la definición y los datos del usuario.

La estructura de Schemas

La estructura tiene mucho sentido si la comparas con la programación orientada a objetos o incluso con una base de datos.

<schemalist>

    <enum>...</enum>

    <schema>

        <key>...</key>

    </schema>

</schemalist>

Creo que entender esto te va a facilitar muchísimo leer cualquier gschema.xml, no solo el de esta extensión.

Podríamos resumir la arquitectura del archivo así:

gschema.xml

    ┌─────────────────────────────────────┐
    │ schemalist                          │
    │                                     │
    │   enum  ← definición reutilizable   │
    │   enum                              │
    │   enum                              │
    │                                     │
    │   schema                            │
    │      key ───────────────┐           │
    │      key ───────┐       │           │
    │      key ───┐   │       │           │
    │             │   │       │           │
    └─────────────┼───┼───────┼───────────┘
                  ▼   ▼       ▼
                enum enum   enum

Nivel 1: <schemalist>

Es simplemente el contenedor principal.

<?xml version="1.0" encoding="UTF-8"?>

<schemalist gettext-domain="gnome-shell-extensions">

    ...

</schemalist>

Podría contener uno o varios <schema> y todos los elementos auxiliares (como los enum) que esos esquemas necesiten.

Piensa en él como una carpeta.
Proyecto
│
├── enums
└── schemas

Nivel 2: Los <enum>

Estos no pertenecen todavía a ningún schema.

<enum id="...">
    ...
</enum>

<enum id="...">
    ...
</enum>

Son definiciones reutilizables. Es como decir:

const BannerPosition = {
    LEFT: 0,
    CENTER: 1,
    RIGHT: 2
};

Todavía nadie la usa. Simplemente existe.

Una analogía en Java

Imagina:

public enum BannerPosition {
    LEFT,
    CENTER,
    RIGHT
}

La clase existe, pero ninguna otra clase la está utilizando todavía.

Al principio los enums pareceran una simple lista de valores; más adelante los estaremos viendo como lo que realmente son: tipos reutilizables , exactamente igual que una enum en Java o un enum en C#. Esa forma de pensarlo te va a facilitar muchísimo entender los siguientes key.

Nivel 3: El <schema>

Aquí empieza el verdadero esquema.

<schema
    id="org.gnome.shell.extensions.notification-center"
    path="/org/gnome/shell/extensions/notification-center/">

Yo lo compararía con una clase.

NotificationCenterSettings
{
    ...
}

Todo lo que esté dentro pertenece a este conjunto de preferencias.

¿Qué es un <schema>?

Es la definición de un conjunto de preferencias. Podríamos decir que representa una "colección" o "espacio de configuración" para una aplicación o componente.

En este caso, todo lo que esté dentro de este <schema> pertenece a la extensión Notification Center.

El atributo id

Es el identificador único del esquema.

id="org.gnome.shell.extensions.notification-center"

Es el nombre que utilizará el programa para acceder a estas preferencias. Por ejemplo, en GJS suele verse algo equivalente a:

new Gio.Settings({
    schema_id: "org.gnome.shell.extensions.notification-center"
});

Es decir:

"Quiero trabajar con el esquema de configuración llamado org.gnome.shell.extensions.notification-center."

Este nombre debe ser único para evitar conflictos con otras aplicaciones o extensiones.

El atributo path

Define la ruta lógica donde GNOME almacenará estas preferencias. 

path="/org/gnome/shell/extensions/notification-center/"

No es una carpeta del disco. Es una ruta dentro del sistema de configuración de GSettings. Todas las claves (key) de este esquema vivirán bajo esa ruta.

¿Por qué ambos?

Porque cumplen funciones distintas:

  • id → identifica el esquema.
  • path → indica dónde residen sus valores dentro del árbol de configuración.
Analogía: Si fuera una biblioteca:

El id sería el nombre de la sección.

El path sería la ubicación donde están guardados los libros.

Biblioteca
│
├── Sección:
│   "Notification Center"
│
└── Estantería:
    /org/gnome/shell/extensions/notification-center/
Concepto Definición
Elemento <schema>
Función Agrupa todas las preferencias (key) de una misma aplicación o extensión.
id Identificador único del esquema, utilizado por el código para abrir y acceder a la configuración.
path Ruta lógica dentro del sistema de configuración de GSettings donde se almacenan los valores.
Origen <schema>, id y path: estándar de GSettings.
Nombre y ruta concretos: decisión del autor siguiendo las convenciones del ecosistema GNOME.

Nivel 4: Los <key>

Aquí sí aparece lo interesante. Cada key representa una preferencia concreta.

<key
    name="banner-pos"
    enum="org.gnome.shell.extensions.notification-center.banner-pos">

Es equivalente a decir: private BannerPosition bannerPos; o en JavaScript: settings.bannerPos

Los key pueden ser de dos formas:

Tipo primitivo:
<key type="i">

Aquí GSettings sabe directamente que almacenará un entero.

Tipo enum:
<key enum="...">

Aquí GSettings entiende automáticamente:

"El tipo de este key es el enum indicado."

Es decir, el type="i" desaparece porque el tipo ya está implícito en el enum.

Lo importante

El enum por sí solo no hace nada.

El key es el que dice:

"Yo utilizo este enum."

Es decir:

enum
     ↑
     │
key ─┘

La jerarquía real

Algunos key apuntarán a determinados enum.

schemalist
│
├── enum
├── enum
├── enum
│
└── schema
      │
      ├── key
      ├── key
      ├── key
      └── key

Analogía con una base de datos

Podría verse así:

Tipos

BannerPosition
-------------
LEFT
CENTER
RIGHT

↓

Configuración

banner-pos → BannerPosition

Primero defines el tipo, luego lo utilizas.

¿Y si un enum nunca se usa?

Recuerda lo que dijimos hace un rato. Tendríamos un... enum huérfano.

Este existe, se complia, pero ningún key hace referencia a él.

¿Los id de los enums pueden ser cortos?

No, en este caso no. El id debe ser completo (fully qualified).

Y hay una razón bastante lógica.

<enum id="org.gnome.shell.extensions.notification-center.new-notification">

Luego más abajo aparece algo como:

<key name="new-notification"
     enum="org.gnome.shell.extensions.notification-center.new-notification">

Fíjate que el key hace referencia al id completo. No hace referencia únicamente a: new-notification

¿Por qué GNOME lo hace así?

Porque los enum viven en un espacio global. Imagina dos extensiones:

Extensión A 
<enum id="new-notification">
Extensión B 
<enum id="new-notification">

¿Cuál debe usar GSettings? No tendría forma de saberlo.

En cambio con nombres completos, nunca habrá conflicto.

org.gnome.shell.extensions.notification-center.new-notification

org.gnome.shell.extensions.my-extension.new-notification

Es exactamente el mismo principio que... Los nombres de paquetes en Java. 

com.oracle...

org.apache...

org.gnome...

O los identificadores D-Bus. O los schemas de GSettings. Todos usan nombres largos para garantizar unicidad.

Y fíjate en otro detalle curioso, schema también tiene un nombre largo. Algo parecido a:

<schema
    id="org.gnome.shell.extensions.notification-center"

Luego desde JavaScript haces:

ExtensionUtils.getSettings(
    "org.gnome.shell.extensions.notification-center"
)

No haces: getSettings("notification-center") Por exactamente el mismo motivo.

¿Podría GNOME haber permitido ids relativos?

Sí, podría haber inventado algo como: <enum id="new-notification"> y que automáticamente perteneciera al schema actual.

Pero los diseñadores de GSettings decidieron que:

Todo recurso debe ser identificable globalmente.

Es una filosofía bastante común dentro de GLib.
