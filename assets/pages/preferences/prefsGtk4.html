Metodología de estudio

Entonces seguimos con prefsGtk4.js, manteniendo la misma metodología:

  • primero entenderemos la estructura general;
  • luego los imports;
  • después las clases y métodos;
  • cada preferencia que aparezca la vamos a relacionar con su key o enum correspondiente del gschema;
  • y vamos a prestar especial atención a cómo los controles de la interfaz leen y escriben esos valores.

Eso nos permitirá entender no solamente qué opción aparece en Preferencias, sino qué hay detrás de cada opción y cómo termina llegando a extension.js.

Nuestra metodología para las clases

Ahora no vamos a interpretar cada variable aisladamente. Si aparece algo como:

let ...
const ...

Primero veremos a qué clase/objeto pertenece y para qué se utiliza y cuando encontremos algo relacionado con:

settings.get_...
settings.set_...

Ahí volveremos inmediatamente al gschema que acabamos de estudiar. Por ejemplo, si aparece:

settings.set_boolean("show-events", ...)

ya sabemos:

show-events
   ↓
type = i
default = 3

Y eso nos permitirá preguntarnos algo todavía más interesante:

¿Por qué una key declarada como type="i" está siendo utilizada con set_boolean()?

Si encontramos algo así, sería una inconsistencia que habría que investigar, no simplemente asumir que está bien.

Ahora podemos tratar cada variable como un nodo de nuestro mapa mental:

Variable
   │
   ├── ¿Qué contiene?
   ├── ¿De qué clase/objeto proviene?
   ├── ¿Dónde se utiliza?
   ├── ¿Qué relación tiene con otras variables?
   └── ¿Qué relación tiene con gschema?

Y cuando me pases la primera línea donde se asigna, no vamos a intentar explicar todo el archivo de golpe. Tomaremos esa variable como punto de partida y seguiremos el bloque de código que le pertenece.

Además, podemos ir construyendo mentalmente algo así:

prefsGtk4.js
│
├── settings
│   └── Gio.Settings → gschema
│
├── Variable A
│   └── ...
│
├── Variable B
│   └── ...
│
└── Variable C
    └── ...

Esto nos va a servir muchísimo cuando volvamos a extension.js, porque ya no estaremos pensando solamente: "¿Qué hace este método?" sino:

"¿Qué objetos maneja este método, de dónde vienen y qué configuración representan?"

Y una pequeña regla que mantendría: si una variable no tiene suficiente contexto en la línea donde se declara, esperamos a ver el bloque que la utiliza antes de sacar conclusiones. Así evitamos repetir el problema que justamente queremos evitar: adelantarnos a la lógica.
