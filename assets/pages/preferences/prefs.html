Prefs.js

Vamos a mantener exactamente la metodología que usamos con gschema.xml: por partes, entendiendo qué hace cada cosa y relacionándola con lo que ya sabemos.

Primer Bloque:

/*
Version 24.00
=============
*/

const Config            = imports.misc.config;
const Extension         = imports.misc.extensionUtils.getCurrentExtension();
const GLib              = imports.gi.GLib;

Comentario de versión

/*
Version 24.00
=============
*/

Es simplemente un comentario utilizado por el autor para indicar la versión del archivo o de la extensión a la que corresponde este código.

No tiene ningún efecto sobre JavaScript y podemos notar algo interesante respecto al gschema que acabamos de estudiar: allí encontramos: current-version = 23.00, mientras aquí aparece: Version 24.00.

No debemos asumir todavía que ambos valores representan exactamente lo mismo. Pueden estar relacionados con diferentes versiones del código, y precisamente esta diferencia es algo que podremos aclarar al estudiar el resto de prefs.js y después volver a current-version.

Config

Aquí se importa el módulo de configuración de GNOME Shell.

const Config = imports.misc.config;

El resultado se guarda en la constante: Config

Por lo tanto, posteriormente el código puede utilizar Config para acceder a información de configuración de GNOME Shell, en lugar de escribir nuevamente la ruta completa. Es básicamente un alias.

Extension

Esta es particularmente importante para una extensión.

const Extension = imports.misc.extensionUtils.getCurrentExtension();

getCurrentExtension() obtiene la información de la extensión que está ejecutando este código.

El resultado se guarda en: Extension.

Esto permite que posteriormente prefs.js pueda acceder a recursos propios de la extensión, por ejemplo:

  • archivos de la extensión;
  • directorios;
  • información de la extensión;
  • recursos que formen parte de su instalación.

Y hay algo que nos interesa especialmente para lo que vamos a estudiar: es muy probable que aquí termine apareciendo el acceso a los recursos de la extensión que necesita la ventana de preferencias.

GLib

Aquí se importa GLib, una de las bibliotecas fundamentales utilizadas por el ecosistema GNOME.

const GLib = imports.gi.GLib;

El código podrá utilizarla mediante: GLib.

Segundo Bloque

Este sorprende porque después de todos esos imports uno esperaría encontrarse con una función init() llena de inicialización… y resulta ser:

function init() {
}

¿Qué significa?

init() probablemente está ahí porque el sistema de preferencias espera que prefs.js tenga una función de inicialización, pero en esta versión concreta Selenium-H no necesita hacer nada especial al inicializar el módulo.

Es decir:

GNOME carga prefs.js
        ↓
puede llamar a init()
        ↓
init() existe
        ↓
no hace nada

No debemos confundirla con las funciones de inicialización que vimos en extension.js. Aquí init() no está inicializando el Notification Center ni cargando las preferencias.

¿Por qué dejar una función vacía?

Hay varias posibilidades razonables:

  1. Compatibilidad con el mecanismo de preferencias de esa generación de GNOME.
  2. Plantilla generada originalmente que el autor mantuvo.
  3. En algún momento pudo haber contenido inicialización y posteriormente fue eliminada.
  4. Simplemente se dejó porque no hacía falta eliminarla.

Con lo que tenemos ahora, no podemos saber cuál de esas fue la razón histórica, pero hay algo que sí podemos afirmar:

Esta init() no tiene ninguna lógica propia actualmente.

Y esto también es una buena oportunidad para nuestra metodología: no todo lo que encontramos necesita tener una función oculta o un propósito complejo. A veces es simplemente una pieza que la estructura del sistema esperaba y que en esta versión quedó vacía.

Tercer Bloque

Ahora sí, aquí aparece el corazón de prefs.js y además este bloque explica por qué existen prefsGtk3.js y prefsGtk4.js. 

function buildPrefsWidget() {

  let gtkVersion = (Config.PACKAGE_VERSION >= "40") ? Extension.imports.prefsGtk4 : Extension.imports.prefsGtk3;
  gtkVersion.init();
  let widget = new gtkVersion.Prefs_NotificationCenterExtension();   
  GLib.timeout_add(GLib.PRIORITY_DEFAULT, 0, ()=> {    
    new gtkVersion.ExtensionPreferencesWindow_NotificationCenterExtension( widget );
    return false;
  });
 
  (Config.PACKAGE_VERSION >= "40") ? null : widget.show_all();  
  return widget;  
  
}

La función

buildPrefsWidget() es la función que construye/devuelve el widget principal de preferencias que GNOME utilizará para mostrar la configuración de la extensión.

function buildPrefsWidget() { ... }

Y aquí aparece una arquitectura interesante:

prefs.js
   │
   ├── ¿GTK3 o GTK4?
   │
   ├── prefsGtk3.js
   └── prefsGtk4.js

Detectar la versión de GNOME/GTK

let gtkVersion = (Config.PACKAGE_VERSION >= "40")
    ? Extension.imports.prefsGtk4
    : Extension.imports.prefsGtk3;

Aquí está usando un operador ternario: condición ? si_verdadero : si_falso.

La condición es: Config.PACKAGE_VERSION >= "40" Es decir:

Si la versión del paquete de GNOME Shell es 40 o superior, utiliza prefsGtk4; de lo contrario, utiliza prefsGtk3.

Por tanto:

GNOME < 40
    ↓
prefsGtk3.js

GNOME >= 40
    ↓
prefsGtk4.js

Y esto nos confirma inmediatamente por qué existen los dos archivos.

No son dos versiones alternativas de las preferencias que el usuario pueda escoger: son implementaciones diferentes utilizadas según la versión de GNOME.

Inicializar el módulo seleccionado

gtkVersion.init();

Aquí gtkVersion ahora contiene uno de estos módulos: prefsGtk3 o prefsGtk4. Por lo tanto, está llamando a: prefsGtk3.init() o prefsGtk4.init().

Esto es importante porque la init() vacía que acabamos de ver no es la única init() del proyecto.

La que acabamos de estudiar: function init() {} pertenece a prefs.js pero aquí se está llamando a: gtkVersion.init() que pertenece al archivo que acabamos de seleccionar.

Así que todavía tendremos que ver qué hace el init() de prefsGtk3.js o prefsGtk4.js.

Crear el widget de preferencias

let widget = new gtkVersion.Prefs_NotificationCenterExtension();

Aquí se crea una instancia de la clase: Prefs_NotificationCenterExtension y nuevamente el archivo concreto depende de GTK.

Por ejemplo: prefsGtk4.Prefs_NotificationCenterExtension o prefsGtk3.Prefs_NotificationCenterExtension. Esto probablemente representa la ventana/contenedor principal de preferencias.

GLib.timeout_add()

Ahora aparece el GLib que vimos al principio:

GLib.timeout_add(GLib.PRIORITY_DEFAULT, 0, ()=> {
    new gtkVersion.ExtensionPreferencesWindow_NotificationCenterExtension(widget);
    return false;
});

Aquí hay algo interesante, está programando una función para ejecutarse mediante el loop de eventos de GLib. El 0 indica que no quiere esperar un intervalo significativo antes de ejecutarla.

Dentro hace: new gtkVersion.ExtensionPreferencesWindow_NotificationCenterExtension(widget); Es decir, crea otra instancia: ExtensionPreferencesWindow_NotificationCenterExtension pasándole el widget que acabamos de crear.

Conceptualmente:

Prefs_NotificationCenterExtension
          │
          ▼
       widget
          │
          ▼
ExtensionPreferencesWindow_...

El detalle de por qué necesita hacerlo mediante timeout_add() lo dejamos pendiente hasta ver prefsGtk3.js/prefsGtk4.js. Ahí seguramente tendrá mucho más sentido.

El return false

Esto es importante en un callback de GLib.

return false;

Al devolver false, está indicando que el callback no debe repetirse. En otras palabras:

Ejecuta esto una vez y no vuelvas a programarlo.

Diferencia GTK3 / GTK4

Finalmente:

(Config.PACKAGE_VERSION >= "40") ? null : widget.show_all();

Otra vez el ternario:

Para GNOME 40 o superior: 
GTK4
→ null
→ no ejecuta show_all()
Para versiones anteriores: 
GTK3
→ widget.show_all()

Esto tiene bastante sentido porque show_all() pertenece al modelo de GTK3 y GTK4 cambió la forma de gestionar la visibilidad de los widgets.

Finalmente devuelve el widget

La función entrega el widget que creó.

return widget;

Por tanto, podemos representar todo el proceso así:

buildPrefsWidget()
        │
        ▼
¿GNOME >= 40?
   │           │
  sí           no
   │           │
   ▼           ▼
prefsGtk4    prefsGtk3
   │           │
   └─────┬─────┘
         ▼
      init()
         │
         ▼
crear Prefs_NotificationCenterExtension
         │
         ▼
GLib programa creación de
ExtensionPreferencesWindow_...
         │
         ▼
¿GTK3?
   │
   ├── sí → show_all()
   │
   └── no → GTK4 gestiona la presentación
         │
         ▼
   return widget

Observación

Aquí aparece algo muy útil para nuestro estudio, sabemos que prefs.js no contiene realmente la interfaz de preferencias.

Es más bien un orquestador/selector:

prefs.js
   │
   ├── detecta versión
   ├── selecciona implementación
   ├── inicializa implementación
   ├── crea los objetos
   └── devuelve el widget

Mientras que la lógica real de la interfaz está en:

prefsGtk3.js
prefsGtk4.js

Por eso tu propuesta de estudiar primero los archivos de preferencias tiene muchísimo sentido. Ahora ya sabemos exactamente dónde buscar.

Y además hemos encontrado algo que deberíamos tener muy presente cuando modernicemos la extensión:

El corte histórico que utiliza Selenium-H es GNOME 40: GTK3 para < 40 y GTK4 para >= 40.

Como nuestro objetivo actual es GNOME moderno, seguramente prefsGtk3.js termine siendo un candidato para estudiar, entender y posiblemente retirar, pero no tomemos esa decisión todavía. Primero veamos qué contiene.

El Resumen

Ahora que sabemos que eso es todo prefs.js, su papel queda bastante claro.

En realidad es un archivo muy pequeño que funciona como puente/orquestador entre GNOME y las implementaciones GTK de las preferencias.

Su estructura completa sería:

prefs.js
│
├── imports
│   ├── Config
│   ├── Extension
│   └── GLib
│
├── init()
│   └── vacío
│
└── buildPrefsWidget()
    │
    ├── Detecta GNOME >= 40
    │
    ├── Selecciona
    │   ├── prefsGtk4.js
    │   └── prefsGtk3.js
    │
    ├── llama init()
    │
    ├── crea Prefs_NotificationCenterExtension
    │
    ├── crea ExtensionPreferencesWindow_...
    │   mediante GLib.timeout_add()
    │
    ├── si GTK3 → widget.show_all()
    │
    └── devuelve widget

Lo más importante que aprendimos

Ahora sabemos que prefs.js no contiene las preferencias propiamente dichas. Su trabajo es básicamente:

Decidir qué implementación de preferencias utilizar y ponerla en marcha.

Por eso ahora tiene mucho sentido pasar a prefsGtk4.js y prefsGtk3.js y yo empezaría por prefsGtk4.js, no por GTK3.

¿Por qué?

Porque nuestro objetivo es modernizar la extensión para GNOME actual, y prefs.js ya nos dijo que:

GNOME < 40  → prefsGtk3.js
GNOME ≥ 40  → prefsGtk4.js

Así que GTK4 es el camino que nos interesa conservar. Después podemos mirar prefsGtk3.js para entender qué hacía originalmente y detectar qué cosas eran solamente compatibilidad histórica.

Y hay otro pequeño punto que podemos dejar anotado:

El ternario de show_all() funciona, pero un if sería más claro.

No necesitamos modificarlo ahora; simplemente lo tenemos identificado para cuando llegue el momento de modernizar.
