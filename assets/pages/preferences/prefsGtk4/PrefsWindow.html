¿Por qué Gtk.Grid?

Gtk.Grid permite colocar widgets en una estructura de filas y columnas. Conceptualmente:

Gtk.Grid

        columna
       0       1       2
    ┌───────┬───────┬───────┐
 0  │       │       │       │
    ├───────┼───────┼───────┤
 1  │       │       │       │
    ├───────┼───────┼───────┤
 2  │       │       │       │
    └───────┴───────┴───────┘

Esto encaja muy bien con una ventana de preferencias, porque podemos tener:

Opción:        [ control ]
Otra opción:   [ control ]
Otra opción:   [ control ]

Así que esta clase probablemente proporciona la estructura visual común que utilizan las diferentes páginas de preferencias.

Pero aquí todavía hay que ser cuidadosos: no sabemos si realmente es una clase base para las cuatro páginas o si simplemente es otro componente reutilizable.

attachLabel: function(KEY, pos)

Aquí aparece el primer método auxiliar y este es bastante interesante porque hace de puente directo entre la interfaz y el gschema.

attachLabel: function(KEY, pos) {
  let prefLabel = new Gtk.Label({
    xalign: 1,
    label: _(settings.settings_schema.get_key(KEY).get_summary()),
    halign: Gtk.Align.START
  });

  this.attach(prefLabel, 0, pos, 1, 1);
}

¿Qué recibe?

El método recibe dos valores:

attachLabel(KEY, pos)
│
├── KEY
│   └── nombre de una key del gschema
│
└── pos
    └── posición/fila donde colocar el label

Aquí KEY es especialmente importante. No recibe directamente: "Show media" sino algo como: "show-media" y a partir de ese nombre busca la información en el schema.

La parte más interesante

Esta expresión: settings.settings_schema.get_key(KEY).get_summary() hace varias cosas encadenadas:

settings
   │
   ▼
settings.settings_schema
   │
   ▼
get_key(KEY)
   │
   ▼
get_summary()

Podemos traducirlo como:

"Ve al schema de estas preferencias, busca la key cuyo nombre es KEY y dame su summary."

Y esto conecta directamente con algo que acabamos de estudiar. Por ejemplo, nuestro gschema tiene:

<key name="show-media" type="b">
    <default>true</default>
    <summary>Show Media Notifications</summary>
    ...
</key>

Si alguien llama: attachLabel("show-media", 0); el método obtiene:

KEY
└── "show-media"

       ▼

       │
       ▼

       │
       ▼
"Show Media Notifications"

Y ese texto termina siendo el contenido del Gtk.Label.

Esto es muy importante

La interfaz no tiene que escribir manualmente el texto de cada opción. El texto ya está definido en el gschema. Así que tenemos:

xalign y halign

El label se crea con:

Aquí hay una pequeña diferencia entre ambos conceptos.

xalign: 1 indica la alineación del contenido del texto dentro del propio label. Mientras que: halign: Gtk.Align.START, indica cómo se posiciona el widget Gtk.Label dentro del espacio que le proporciona el Gtk.Grid.

No necesitamos profundizar más ahora; lo importante para nuestro mapa es que se está preparando el label para formar parte de la cuadrícula.

prefCombo: function(KEY, pos, options, items)

Aquí aparece otro método auxiliar muy importante. prefCombo() ya no solo construye la interfaz: lee una key del gschema, crea un selector y escribe nuevamente en GSettings cuando el usuario cambia la opción.

prefCombo: function(KEY, pos, options, items) {
  
    let SettingCombo = new Gtk.ComboBoxText();
    for (let i = 0; i < options.length; i++) {
      SettingCombo.append(options[i],  items[i]);
    }
    SettingCombo.set_active(options.indexOf(settings.get_string(KEY)));
    SettingCombo.connect('changed', Lang.bind(this, function(widget) {
      settings.set_string(KEY, options[widget.get_active()]);
      reloadExtension();
    }));
    
    this.attachLabel(KEY,pos);
    this.attach(SettingCombo, 1, pos, 1, 1);
    
  }

Los cuatro parámetros

prefCombo: function(KEY, pos, options, items) {

│
├── KEY
│   └── nombre de la key de GSettings
│
├── pos

Aquí aparece una distinción muy importante: options y items no son necesariamente lo mismo. Por ejemplo, podría tener conceptualmente:

options = ["dot", "count"];
items   = ["Dot", "Count"];

El usuario ve: Dot y Count pero el programa guarda: "dot" y "count". Esto encaja directamente con nuestros enums del gschema.

Crea el ComboBox

let SettingCombo = new Gtk.ComboBoxText();

Creamos un selector de texto:

Gtk.ComboBoxText
└── lista desplegable

Llena las opciones

    SettingCombo.append(options[i], items[i]);

Aquí está la relación:

options[i]
    │
    └── valor interno / ID

items[i]
    │
    └── texto visible

Y: append(options[i], items[i]) agrega cada opción al ComboBox. Por ejemplo:

options              items
────────────         ─────────────
"dot"       ───────► "Dot"
"count"     ───────► "Count"

Lee el valor actual de GSettings

Esta línea es fundamental.

SettingCombo.set_active(
    options.indexOf(settings.get_string(KEY))
);

Primero: settings.get_string(KEY) lee el valor actual almacenado.

Supongamos: KEY = "new-notification" y en GSettings actualmente tenemos:"dot". Entonces: options.indexOf("dot") devuelve, por ejemplo: 0 y: SettingCombo.set_active(0); hace que el ComboBox muestre Dot.

Así que el flujo es:

GSettings
    │
    │ get_string(KEY)
    ▼
valor guardado
    │
    │ indexOf()
    ▼
posición dentro de options
    │
    ▼
ComboBox
    │
    ▼
opción visible

¿Qué ocurre cuando el usuario cambia la opción?

SettingCombo.connect('changed', Lang.bind(this, function(widget) { ... }

Se conecta la señal: changed. Cuando el usuario selecciona otra opción, se ejecuta la función. Y aquí viene la operación inversa:

settings.set_string(
    KEY,
    options[widget.get_active()]
);

Es decir:

  1. Obtiene qué posición seleccionó el usuario.
  2. Busca esa posición en options.
  3. Guarda ese valor en GSettings.

Ejemplo:

Usuario selecciona:
    Count
       │
       ▼
get_active() → 1
       │
       ▼
options[1] → "count"
       │
       ▼
settings.set_string(KEY, "count")

Por tanto:

GSettings ──────► ComboBox
   ▲                 │
   │                 │ usuario cambia
   │                 ▼
   └────────────── nuevo valor

Es un flujo bidireccional entre la preferencia y la interfaz.
