Versión del archivo

Es un comentario, así que no afecta al programa.

/*
Version 23.05
=============
*/

Y nuevamente vemos algo interesante:

  • prefs.js decía 24.00
  • prefsGtk4.js dice 23.05
  • gschema tenía current-version 23.00

No debemos intentar reconciliarlos todavía. Claramente no representan necesariamente el mismo concepto de versión. Lo dejamos anotado porque cuando encontremos cómo Metadata o current-version se utilizan, podremos aclararlo.

Config

Ya lo conocemos de prefs.js.

Proporciona información de configuración de GNOME Shell, y en prefs.js lo utilizábamos para decidir:

GNOME < 40 → GTK3
GNOME ≥ 40 → GTK4

Aquí probablemente vuelva a utilizarse para alguna comprobación relacionada con la versión.

¿Qué es realmente settings?

Podemos pensarlo como el objeto que permite a prefsGtk4.js trabajar con las configuraciones definidas en el gschema.

Por ejemplo, posteriormente podremos encontrar algo como: settings.get_boolean("show-media") o settings.set_boolean("show-media", true).

Y ahora sabemos exactamente qué significa: 

settings
           ↓
        schema
           ↓
        key: show-media
           ↓
        type: b
           ↓
        default: true/false según el schema

Esto es justamente el contexto que queríamos obtener antes de volver a extension.js.

Nota importante

El gschema no es el que está siendo leído directamente cada vez que el usuario cambia una preferencia.

Aquí: ExtensionUtils.getSettings(...) se obtiene el objeto de configuración.

Después ese objeto es el que permite: get_*() y set_*() sobre las keys.

Así que podemos visualizarlo como:

gschema.xml
            │
            │ define
            ▼
        GSettings schema
            │
            │ getSettings()
            ▼
        settings
            │
            ├── get_*
            └── set_*
                   │
                   ▼
             valores del usuario

Y esto también confirma algo que habíamos hablado cuando terminamos gschema: el archivo XML define el contrato, pero los valores que el usuario modifica viven fuera del XML.

function reloadExtension () { ... }

Aquí aparece algo interesante porque acabamos de encontrar quién utiliza reload-signal, uno de los keys que dejamos pendientes en el gschema. 

function reloadExtension () {
        
          (settings.get_boolean("reload-signal"))
            ? settings.set_boolean("reload-signal", false)
            : settings.set_boolean("reload-signal", true);
        
        }

¿Qué está haciendo?

Primero lee: settings.get_boolean("reload-signal")

Recordemos del gschema:

<key name="reload-signal" type="b">
            <default>false</default>
            ...
        </key>

Por lo tanto, obtiene un true o false.

Después hace lo contrario, es decir, invierte el valor de reload-signal.

true  → false
        false → true

¿Por qué se llama reloadExtension()?

Aquí empieza lo interesante, el método no está recargando directamente la extensión.

No encontramos algo como:

Extension.disable();
        Extension.enable();

Ni un comando de GNOME para recargarla, en cambio hace esto:

reloadExtension()
               │
               ▼
        lee reload-signal
               │
               ▼
        invierte el valor
               │
               ▼
        GSettings cambia
               │
               ▼
        otra parte de la extensión detecta el cambio
               │
               ▼
        ¿recargar?

Por lo tanto, reload-signal funciona como un interruptor/señal de comunicación entre prefsGtk4.js y extension.js.

Y esto explica perfectamente por qué el key existe en la sección: Extension Variables del gschema.

¿Por qué no simplemente poner true?

Imaginemos que inicialmente:

reload-signal = false

Si hacemos: settings.set_boolean("reload-signal", true); podemos provocar un cambio.

Pero si posteriormente queremos volver a solicitar otra recarga: settings.set_boolean("reload-signal", true); ya no hay cambio de valor.

En cambio, haciendo esto, cada llamada genera un cambio de configuración.

false → true
        true → false
        false → true
        true → false
        ...

Eso permite que otra parte del programa pueda estar escuchando el cambio:

false → true   → ¡cambió!
        true → false   → ¡cambió!
        false → true   → ¡cambió!

Por eso reload-signal es mejor entendido como un toggle utilizado como señal, no como una configuración cuyo estado tenga significado permanente.

Esto también explica el nombre. No es: reload = true sino: reload-signal porque el valor en sí no representa "la extensión debe estar recargada".

Representa:

"Algo cambió; presta atención a esta modificación."

El significado está en la transición, no en que el valor final sea true o false.

Una pieza que antes nos faltaba

En el gschema vimos:

reload-signal
            default: false

No sabíamos quién lo modificaba. Ahora sabemos:

prefsGtk4.js
              │
              │ reloadExtension()
              ▼
        reload-signal
              │
              │ cambio de false ↔ true
              ▼
        ¿algún listener en extension.js?
              │
              ▼
        recargar extensión

Y aquí sí vale la pena detenernos.

No necesitamos buscar todavía otra cosa: cuando volvamos a extension.js, una de las cosas que debemos localizar es quién está escuchando reload-signal.

Ahí podremos confirmar exactamente qué significa "reload" en esta extensión y qué proceso realiza Selenium-H cuando el usuario pulsa la opción correspondiente en Preferencias.

Ese será un ejemplo perfecto de cómo gschema + prefsGtk4 + extension.js terminan formando una sola pieza de lógica.

function reloadApplicationProfiles () { ... }

Este es prácticamente el gemelo especializado de reloadExtension() que acabamos de ver.

function reloadApplicationProfiles() {

  (settings.get_boolean("reload-profiles-signal"))
    ? settings.set_boolean("reload-profiles-signal", false)
    : settings.set_boolean("reload-profiles-signal", true);

}

¿Qué hace?

Lee específicamente: settings.get_boolean("reload-profiles-signal") y luego invierte su valor: 

false → true
true  → false

Exactamente el mismo mecanismo que:

reloadExtension()
    ↓
reload-signal

Pero ahora:

reloadApplicationProfiles()
    ↓
reload-profiles-signal

Y recordemos que en el gschema encontramos:

<key name="reload-profiles-signal" type="b">
    <default>false</default>
    ...
</key>

Así que ya tenemos otra conexión directa entre el gschema y prefsGtk4.js.

¿Por qué invertirlo?

Por exactamente la misma razón que antes. No importa si termina en true o false; lo importante es que el valor cambie. Por ejemplo:

Estado inicial:
reload-profiles-signal = false

Usuario realiza una acción:
false → true

Eso genera un cambio detectable. Si vuelve a realizar la acción: true → false

Tenemos otro cambio detectable, Es básicamente un toggle utilizado como señal.

A partir de aquí, cada vez que aparezca settings, ya no tenemos que preguntarnos "¿de dónde sale esto?". Sabemos que estamos trabajando con las keys que acabamos de estudiar.

Una nota para el futuro 

settings = ExtensionUtils.getSettings(
    "org.gnome.shell.extensions.notification-center"
);

Esto lo debemos marcar como una dependencia del cambio de nombre, no como un simple texto que podemos reemplazar superficialmente.

Ese string es el ID del schema de GSettings. Por lo tanto, si algún día cambiamos el identificador de la extensión, no basta con cambiar el nombre visible o el UUID.

Tendremos que revisar, como mínimo:

org.gnome.shell.extensions.notification-center
        │
        ├── prefsGtk4.js
        ├── prefsGtk3.js
        ├── gschema.xml
        ├── cualquier otro código que haga getSettings()
        └── cualquier referencia adicional

Y en el gschema tenemos además:

<schema
    id="org.gnome.shell.extensions.notification-center"
    path="/org/gnome/shell/extensions/notification-center/">

Así que ahí tenemos dos referencias relacionadas:

  • id → identidad del schema.
  • path → ruta donde se almacenan los valores de ese schema.

No necesariamente debemos cambiar ambos por obligación, pero sí debemos decidirlo conscientemente si cambiamos la identidad de la extensión.

Queda anotado como tarea para la fase de renombrado: hacer una búsqueda global de org.gnome.shell.extensions.notification-center y revisar cada aparición antes de modificarla.

Corrección metodológica

No debemos asumir todavía que reloadExtension() solo existe para comunicarse con extension.js.

Tenemos tres posibilidades:

reloadExtension()
       │
       ├── llamada desde prefsGtk4.js
       │
       ├── llamada desde otro archivo de preferencias
       │
       └── llamada desde extension.js u otro componente

Y también puede ocurrir que la función esté definida pero no se utilice actualmente, algo que ya hemos encontrado en este proyecto.

Por ahora lo correcto es registrar únicamente lo que sabemos de reloadExtension():

Lo que sabemos
  1. Lee reload-signal.
  2. Invierte su valor.
  3. Al hacerlo, genera un cambio en GSettings.
Lo que todavía NO sabemos
  • quién llama a reloadExtension();
  • quién escucha reload-signal;
  • qué hace el receptor cuando cambia;
  • si realmente provoca una recarga completa;
  • si existe alguna otra función de prefsGtk4.js que dependa de ella.

Así que cuando sigamos recorriendo este mismo archivo, si encontramos una llamada: reloadExtension(); la conectamos inmediatamente.

Y cuando terminemos prefsGtk4.js, podemos hacer una búsqueda específica de:

reloadExtension
reload-signal

Para cerrar el circuito dentro del archivo antes de pasar a extension.js.

Algo que me parece más interesante

Ahora tenemos dos mecanismos muy parecidos:

reloadExtension()
        │
        └── reload-signal
             → recargar extensión


reloadApplicationProfiles()
        │
        └── reload-profiles-signal
             → recargar perfiles de aplicaciones

Pero, igual que dijiste anteriormente, todavía no debemos asumir quién los llama ni quién los recibe.

Este archivo puede contener llamadas a: reloadApplicationProfiles(); más adelante y también podría existir algún listener en extension.js.

Por eso nuestro mapa queda:

                 prefsGtk4.js
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
 reloadExtension()     reloadApplicationProfiles()
          │                       │
          ▼                       ▼
 reload-signal       reload-profiles-signal
          │                       │
          └───────────┬───────────┘
                      ▼
              ¿quién escucha?
                      │
              todavía pendiente

Y esta vez tenemos una pista adicional: el segundo signal confirma que "Application Profiles" no es simplemente una lista de aplicaciones, sino que existe algún mecanismo específico para volver a cargar/reprocesar esos perfiles.

Cuando encontremos las funciones que llaman a estas dos funciones dentro de prefsGtk4.js, podremos empezar a entender qué acción del usuario provoca cada señal.

Los únicos métodos definidos

Si esos son los únicos métodos definidos en prefsGtk4.js y a partir de aquí aparecen variables o clases, entonces podemos separar claramente dos responsabilidades.

Lo que acabamos de encontrar

prefsGtk4.js
│
├── init()
│
├── reloadExtension()
│   └── cambia reload-signal
│
└── reloadApplicationProfiles()
    └── cambia reload-profiles-signal

Esos tres son los métodos propios que hemos visto hasta ahora y ahora, si empiezan las variables, probablemente estamos entrando en la definición de las clases/objetos que construyen la interfaz de preferencias.

Esto también explica por qué prefs.js necesitaba hacer: new gtkVersion.Prefs_NotificationCenterExtension() porque esa clase tiene que estar definida en algún punto de este archivo.
