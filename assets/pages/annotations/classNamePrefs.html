ClassName_NotificationCenterExtension

En las clases de las preferencias del archivo PrefsGtk4.js, los nombres de cada clase viene acompañado de "_NotificationCenterExtension".

Por ejemplo:

const PrefsWindow_NotificationCenterExtension = new GObject.Class({
    Name: "PrefsWindow_NotificationCenterExtension",
    Extends: Gtk.Grid,
});

¿Esto es necesario incluirlo en el nombre las clases?

No, no es necesario incluir NotificationCenterExtension en cada nombre. En este proyecto es principalmente una convención de nomenclatura que utilizó Selenium-H, no una exigencia de GObject, GTK ni JavaScript.

Podría llamarse perfectamente:

const PrefsWindow = new GObject.Class({
    Name: "PrefsWindow",
    Extends: Gtk.Grid,
});

Siempre que no haya conflictos de nombres y las referencias se actualicen correctamente.

¿Por qué lo hizo Selenium-H?

Probablemente para dejar claro el ámbito de pertenencia de cada clase.

Mira la cantidad de algunas clases:

ExtensionPreferencesWindow_NotificationCenterExtension
ExtensionResetButton_NotificationCenterExtension
Prefs_NotificationCenterExtension
PrefsWindow_NotificationCenterExtension
PrefsWindowForNotifications_NotificationCenterExtension
PrefsWindowForCalendar_NotificationCenterExtension
PrefsWindowForIndicator_NotificationCenterExtension
PrefsWindowForAppList_NotificationCenterExtension

Sin el sufijo son mucho más fáciles de leer:

ExtensionPreferencesWindow
ExtensionResetButton
Prefs
PrefsWindow
PrefsWindowForNotifications
PrefsWindowForCalendar
PrefsWindowForIndicator
PrefsWindowForAppList

¿Qué inconveniente tiene mantenerlo?

Principalmente ruido visual. Por ejemplo:

this.notificationPrefs =
    new PrefsWindowForNotifications_NotificationCenterExtension();

Frente a:

this.notificationPrefs =
    new PrefsWindowForNotifications();

La segunda nos permite concentrarnos en qué hace la clase, en lugar de repetir constantemente a qué extensión pertenece y esto encaja perfectamente con una de tus decisiones anteriores para el proyecto: no queremos reinventar ni renombrar cosas sin necesidad.

¿Podríamos considerar eliminar el sufijo?

Yo lo trataría así para RE: Notification Center, no cambiaría todos esos nombres solamente por estética.

Primero determinaría si el cambio de nombre de la extensión nos obliga a modificar alguna referencia. Si no existe una razón técnica, podemos dejarlos. Pero si durante la modernización vamos a tocar esas clases de todas formas, sí podríamos considerar eliminar el sufijo como una limpieza de código, siempre que hagamos el cambio de forma consistente.

Y hay una razón adicional para no apresurarnos: en GObject tenemos dos nombres relacionados:

const PrefsWindow_NotificationCenterExtension = ...

Y:

Name: "PrefsWindow_NotificationCenterExtension"

Si cambiamos uno, tenemos que revisar el otro y todas las referencias a la clase. Así que lo podemos dejar como una posible mejora de nomenclatura, pero no como una tarea prioritaria.

En resumen:

No es obligatorio. Es una convención del autor original.

Y para nuestro proyecto mantendría la filosofía que ya definimos: conservar nombres existentes salvo que haya una razón concreta para cambiarlos.

Carga visual innecesaria

En una situación ordinaria sería algo como:

Le pedí el nombre y me dio el árbol genealógico completo.

Exactamente. Es como:

—¿Cómo te llamas?
—Carlos.
—Perfecto.
—Carlos Rodríguez Pérez, hijo de Juan Rodríguez Pérez y nieto de...
—¡Carlos estaba bien!

Y aquí pasa exactamente eso: PrefsWindow_NotificationCenterExtension.

Cuando para entender el código lo que realmente necesitamos recordar es: PrefsWindow.

El resto es información repetida en prácticamente todas las clases. De hecho, mientras estabamos haciendo este mapa mental, ese sufijo nos perjudica un poco porque aumenta la carga visual. Si tenemos: 

PrefsWindowForNotifications_NotificationCenterExtension
PrefsWindowForCalendar_NotificationCenterExtension
PrefsWindowForIndicator_NotificationCenterExtension
PrefsWindowForAppList_NotificationCenterExtension
...

Nuestro cerebro tiene que procesar varias veces: _NotificationCenterExtension para encontrar las diferencias importantes: 

Notifications
Calendar
Indicator
AppList
...

Así que durante nuestro análisis podemos hacer algo muy sencillo: mentalmente lo tratamos como un apellido que ya conocemos. Por ejemplo:

PrefsWindow_NotificationCenterExtension
        ↓
PrefsWindow

PrefsWindowForNotifications_NotificationCenterExtension
        ↓
PrefsWindowForNotifications

El código no vamos a modificarlo todavía, cuando llegue el momento de modernizar el proyecto, podemos decidir si vale la pena quitar esa repetición. No porque técnicamente sea necesario, sino porque la legibilidad también es parte del mantenimiento del código.

De hecho, me parece una buena regla para nuestro proyecto:

No cambiar un nombre porque sea viejo; cambiarlo si el nuevo nombre hace que el código sea más claro o si la modernización lo requiere.

Alternativas del nombre

Entre las opciones para modificar el nombre, tenemos:

  • Eliminar por completo la parte de *_NotificationCenterExtension
  • Colocarlo al inicio NotificationCenterExtension_*
  • Reducirlo a las iniciales *_NCE

Las tres opciones son técnicamente posibles, pero yo descartaría _NCE y NotificationCenterExtension_ para este proyecto.

Las tres opciones

Eliminarlo por completo

Es la opción más limpia. El contexto ya está dado por el propio proyecto/archivo.

PrefsWindow
PrefsWindowForNotifications
PrefsWindowForCalendar
PrefsWindowForIndicator
PrefsWindowForAppList

Por ejemplo:

this.notificationPrefs =
    new PrefsWindowForNotifications();

Se entiende inmediatamente.

Reducirlo a _NCE

Es más corto, pero introduces una abreviatura que tenemos que recordar.

PrefsWindow_NCE
PrefsWindowForNotifications_NCE

Y terminamos pasando de:

"¿Qué significa toda esta cola?"

a:

"¿Qué significaba NCE?"

No ganamos demasiado.

Ponerlo al principio

Personalmente me parece peor para este caso. Sí agrupa alfabéticamente todas las clases de la extensión, pero vuelve todavía más difícil identificar rápidamente qué hace cada clase. 

NotificationCenterExtension_PrefsWindow
NotificationCenterExtension_PrefsWindowForNotifications

¿Cúal elegiría?

Para RE: Notification Center, yo elegiría esta convención:

Prefs
PrefsWindow
PrefsWindowForNotifications
PrefsWindowForCalendar
PrefsWindowForIndicator
PrefsWindowForAppList
ExtensionPreferencesWindow
ExtensionResetButton
UpdatePage

Es decir, que el nombre describa la función de la clase y nada más. Además, esto combina muy bien con lo que estamos haciendo ahora: cuando construimos el mapa mental, podemos reconocer inmediatamente:

Prefs
 └── Gtk.Stack

PrefsWindow
 └── Gtk.Grid

PrefsWindowForNotifications
 └── preferencias de notificaciones

PrefsWindowForCalendar
 └── preferencias del calendario

PrefsWindowForIndicator
 └── preferencias del indicador

PrefsWindowForAppList
 └── perfiles/aplicaciones

Muchísimo más fácil de leer.

En la fase de modernización, podemos hacer una pasada específica de limpieza de nomenclatura y cambiar todos los nombres de manera consistente.

Y si finalmente eliminamos _NotificationCenterExtension, habrá que cambiar tanto:

const PrefsWindow_NotificationCenterExtension = ...

Como: Name: "PrefsWindow_NotificationCenterExtension" y todas las referencias:

new PrefsWindow_NotificationCenterExtension()

Así que sería una modificación sistemática, no algo que convenga hacer a mitad de la investigación. Lo anotaría como una posible mejora de nomenclatura del proyecto: eliminar el sufijo _NotificationCenterExtension por redundante, salvo que durante la revisión descubramos alguna razón técnica para conservarlo.
